## Why this is one program, not one entangled patch

- **One project-level plan and dependency/risk board.** All eight tracks share a frozen core-interface understanding, performance budget policy, experience rubric, evidence ledger, and owner approval requirements.
- **Eight separately owned implementations.** Each E## retains its original slot, mapped identities, old class and independent candidate path. No worker may edit another worker's candidate directory or modify shared host code.
- **One cross-exhibit closeout.** Run relevant regression and resource tests after the tracks complete, and produce one consolidated matrix comparing each candidate with its incumbent. A working build does not prove a superior experience.
- **No one-shot monolithic source dump.** Build a real prototype, validate it, record evidence, and only then advance. Parallel work is permitted only for non-overlapping files; default to one or two active workers to reduce local CPU/RAM and quota pressure.
- **Do not silently shift media.** The eight source commissions are bounded in-bay replacements. The canonical Bible separately records speculative exhibit-triggered pocket-world exploration for other scenes; that is not authority to redesign these eight into a new portal framework.

## Implementation and integration boundaries

- Implement all eight **actual playable prototypes**, not merely a master plan, static placeholder, tutorial, web UI mockup, or set of screenshots. Each prototype must be executable through an isolated preview of approximately the same bay footprint, without introducing a second museum runtime inside production.
- Use existing vanilla TypeScript and current pinned Three.js. The frozen ExhibitModule lifecycle is `preload(ctx)`, `mount(ctx)`, `activate()`, `update(dt, ctx)`, `deactivate()`, `unmount()`, `dispose()`, `reset()`, `getAccessibleContent()`. Prefer the existing ExhibitBase and ResourceScope patterns. All update timing comes from the museum host. No global camera, controls, renderer, loop or persistence owner.
- Keep exhibit geometry inside the configured bay bounds, leave visitor route and collision unchanged, respect current tier/transfer budgets, avoid per-frame allocations, use original/provenance-authorized art, and do not introduce unsupported network calls or global CSS.
- Maintain existing project-first plaque and lectern information plus accessible DOM descriptions for all essential meaning. All core decisions need keyboard and touch alternatives; provide reduced motion, low-detail option and muted-by-default audio when relevant.
- Require a visible causal interaction and at least two substantially distinct outcomes per candidate, as described by each workstream below. One playthrough must be repeatable identically; offer reset/undo or branch replay as specified.
- Preserve historical/canonical source states, classify demonstration fixtures as fictional/synthetic and do not infer missing source or character references. No spiders or spider-like substitutes, no disallowed content and no generic substituted character art.
- Do not change active exhibit registration or physical museum code. Stage work strictly in each candidate root, with test and preview fixtures colocated. If a shared candidate-only preview helper is necessary, propose its owner/path first, restrict it to experiments and serialize changes to that helper.
- Prefer one isolated Git worktree or branch per E##. Each track may produce one local review branch and **one draft PR per candidate only when GitHub access and authorization are confirmed**. Never self-merge. A project-wide index/review branch may summarize results but must not enable any of the eight candidates in the live registry.

## Acceptance matrix (do not mark a row PASS without evidence)

Each E## must satisfy these independent gates:

- **Purpose:** the replacement teaches its actual source project better than the incumbent; show one source-grounded changed-understanding hypothesis and a comparative verdict of ACCEPT FOR REVIEW, REVISE, NO IMPROVEMENT, or BLOCKED.
- **Experience:** opening state, first action, at least two meaningful visitor decisions and outcomes, an earned signature reveal, end condition and exact replay/reset tested; no fixed button-only sequence dressed up with effects.
- **Truth:** source-backed claims distinguished from synthetic demonstration content and UNKNOWN data; asset licenses and permissions known; no invented canonical content.
- **Runtime:** actual source code runs with host-compatible lifecycle and browser preview; focus on real behavior, not solely typecheck or CI assertions.
- **Accessibility:** all essential choices and results available with keyboard/touch and DOM equivalents; visible focus and reduced motion. Sound is optional and muted initially.
- **Performance:** compare to incumbent or tier limits with measured (not guessed) sizes/resource counts; disposal returns exhibit-owned resources to zero after repeated mounting/reset/unmount cycles; no extra render loop or external runtime dependencies.
- **Scope:** diff contains only authorized candidate, fixture, test, preview and documentation files; no changed production registry, existing world/renderer/visitor movement, Secrets, Builder, Workshop, source mapping, `main` or `pages-preview`.
- **Verification:** record exact commands run, observed exit status, browser evidence (with screenshots only when actually captured), status `IMPLEMENTED`, `VERIFIED`, `PARTIAL`, `BLOCKED` or `UNVERIFIED`, and a restoration path. Broken/untested gates cannot be described as successful.

Validation ladder: targeted type/lint/schema -> affected state/unit tests -> browser user-journey and lifecycle/disposal -> applicable museum regression/build/resource/offline checks. Expand to cross-repo tests only if the candidate affects a shared surface. Never weaken existing checks to make results pass. One coherent implementation pass and at most one targeted repair pass PER candidate; thereafter report the precise gap and proceed to another independent workstream if safe.
